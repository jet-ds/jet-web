## Intent and scope

Ship a durable correction for the Blob transfer incident without moving the media library into Git or making Astro builds process the library. Keep the static Astro application, MDX content, existing design system and explicit operator publishing workflow. Release this as **2.4.0**: the new media workflow is a minor feature release, delivered with hotfix urgency.

The user approved Vercel Blob for both storage roles: a separate private store for originals and the existing public store for optimized delivery assets. Media binaries remain external; Git contains content and small descriptors. The source files and unfinished notes already present locally must be preserved.

The investigation established that direct requests for the roughly 2 MB Spider-Man PNG dominate the currently visible Blob transfer. Its historic requester identity remains unknown. Changing metadata alone does not stop requests to that existing URL. Optimized public downloads continue to consume Blob transfer; this design reduces bytes and prevents new anonymous access to originals, rather than promising unlimited free bandwidth.

- Retain Node.js 24.x, Astro 7, React 19, strict TypeScript 6, npm and the existing pinned dependencies. Use the already installed Sharp and `@vercel/blob`; no new application service or image-processing dependency is required.
- Keep static hosting: no Astro server adapter, request-time image proxy, runtime transformation service or public originals-download endpoint.
- Preserve publication eligibility, Blog/Works ordering, finite carousels, dark/light artwork, alt text, intrinsic dimensions, layout, accessibility and metadata identity relationships.
- Builds and routine tests do not require or use storage credentials and perform no media network reads or external writes. Publishing is separate from building.
- The default committed `public/images/og-default.jpg` and its shared metadata contract remain unchanged.
- Work on `codex/blob-transfer-2.4.0`, based on `46149edf72d300120e6e147d202392f2733931d9`. The existing untracked 2.4.0 build-notes document stays outside this change unless explicitly requested.

## Storage and authorization boundaries

1. **Private originals:** create a public-inaccessible Vercel Blob store named `jet-web-originals`, in HKG1, in `jet-sanchezs-projects`. Preserve raw source bytes and provenance here. Confirm team, region and private access before its first write. Do not change the access mode of the existing public store.
2. **Public renditions:** continue using `jet-web-blob` / `store_vYgE4WbMW8JGD8rh`. Publish only bounded, explicitly generated renditions under a new versioned path namespace. Never overwrite legacy objects or silently replace a URL's bytes.
3. **Operator credentials:** the existing public-store credential remains separate from the private-originals credential. Use `BLOB_READ_WRITE_TOKEN` for the existing public store and a dedicated `BLOB_ORIGINALS_READ_WRITE_TOKEN` for originals. These are operator-only local inputs; no token, signed URL or private-original URL enters Git, HTML, client props, generated corpus or logs. Do not connect originals credentials to routine CI or static deployments.
4. Explicitly bind each write to the intended store and access mode rather than relying on ambiguous default store selection. Missing or mismatched credentials fail before publishing. Do not print SDK request headers or raw credential-bearing errors.

Creating the private store, publishing replacement assets and migrating originals are within the agreed storage change. Billing upgrades, unrelated project changes, deployment/merge and deletion of existing public objects are separate operations; do not perform them implicitly during image preparation.

## Image identity and checked-in descriptors

Use one small JSON descriptor per asset under `src/data/media/<lane>/<slug>.json`. The asset key is `<lane>/<slug>`, where lane is `about`, `blog` or `works`. Keep alternative text in the consuming content because its meaning belongs to the context of use.

Each descriptor records:

- `schemaVersion: 1` and a nonempty pipeline version;
- source SHA-256, decoded source format and actual oriented source dimensions;
- the finite generated rendition set, each with role, immutable public URL, actual format, width, height, byte length and SHA-256;
- no credentials, signed URLs, private hostnames or private-original URLs.

Blog and Works frontmatter reference `image.asset` and `image.alt`, with optional `image.darkAsset` for Works. About uses the same asset key/resolver in page code. Source dimensions remain a validated 1920x1080 for published Blog/Works, and a 3:4 source of at least 1200x1600 for About, within the same 64-megapixel cap. Migration decoded the existing About original as 3060x4080; 1200x1600 is its largest delivery rendition, not its source size. Preserve those actual source dimensions and raw bytes. Drafts can remain incomplete; published records cannot.

Descriptor resolution is local and synchronous. Unknown asset keys, untracked descriptors used by published content, wrong lane, invalid dimensions, unsupported schema versions, missing variants, unsafe URLs or byte-budget violations are publication/build errors. There is no legacy-original URL fallback in the final migrated application. Reject direct authored `image.url`/`darkUrl` fields after migration so the old bypass cannot recur.

Only explicit public rendition data is serialized into collection records and browser islands. Every consumer receives dimensions belonging to the URL it actually renders; original dimensions must never be attached to a smaller rendition.

## Processing once at upload time

Keep the operator entry point `npm run upload-image <lane>/<filename>`. Refactor its reusable operations into small testable modules, rather than adding an independent uploader that bypasses it.

Move staging outside the served tree to ignored `Untracked/media-staging/<lane>/`. `public/images-staging/` is unsafe for private sources because Astro can copy its files into a deployment. Preserve any existing staged bytes, relocate them only through an explicit checked migration, and make the build reject staged source media remaining under `public/`. Keep the existing `.gitkeep` lane markers; never silently delete local progress.

The command performs these ordered actions:

1. Validate the lane, kebab-case slug, canonical filesystem containment, regular-file input, supported format and bounded decode. Reject traversal and symlinks escaping staging. Maximum source size is 20 MiB and decoded input is capped at 64 megapixels. Reject animated/multipage inputs with an explicit error rather than silently dropping animation.
2. Decode and orient with Sharp, verify the required aspect/dimensions for the lane, hash the original bytes, and generate all required renditions locally. Do not upscale or silently crop artwork.
3. Validate the complete rendition set and budgets before any upload.
4. Store the original privately at an immutable path incorporating lane, slug and full source hash. Store renditions publicly at paths incorporating lane, slug, source hash, pipeline identity, role and full output hash. Use `addRandomSuffix: false`, no overwrites and a one-year cache lifetime.
5. Verify successful writes and metadata. Reuse a previously verified object on repeat execution only when the complete expected immutable identity and metadata match; unexpected pre-existing objects fail safely.
6. Write the descriptor atomically only after all required objects are verified. Print the asset key and a safe summary for frontmatter adoption.

Interrupted operations can leave unreferenced immutable objects, but never a published partial descriptor. Keep an ignored operation journal under `Untracked/media-operations/` so reruns can resume verified work. Never automatically delete objects as rollback. A changed source or processing recipe creates a new immutable version, preserving old descriptors' rollback targets.

Using Sharp locally avoids requiring a new OIDC setup solely for optimization. The installed SDK also supports `putImage`, but its OIDC requirement is unnecessary for this design's existing explicit local publishing path.

## Rendition contract, version 1

Use a finite set so storage grows linearly with assets, rather than allowing arbitrary request-time transformations.

| Source lane  | Public role       | Dimensions | Format | Maximum encoded bytes |
| ------------ | ----------------- | ---------- | ------ | --------------------- |
| Blog / Works | responsive-small  | 480x270    | WebP   | 60,000                |
| Blog / Works | responsive-medium | 960x540    | WebP   | 160,000               |
| Blog / Works | carousel          | 1152x648   | WebP   | 220,000               |
| Blog / Works | responsive-large  | 1440x810   | WebP   | 300,000               |
| Blog / Works | detail            | 1920x1080  | WebP   | 500,000               |
| Blog / Works | social            | 1200x675   | JPEG   | 200,000               |
| About        | portrait-small    | 400x533    | WebP   | 100,000               |
| About        | portrait-medium   | 800x1067   | WebP   | 200,000               |
| About        | portrait-detail   | 1200x1600  | WebP   | 350,000               |

Portrait intermediate heights use aspect-preserving rounding; decode the result to record the actual dimensions. A one-pixel rounding difference is allowed only for those intermediate portrait roles. JPEG social output uses a white background when flattening transparency. Strip source metadata from public output. Start at WebP quality 82 / JPEG quality 80, with explicit bounded retries down to quality 70 to meet budgets. If the budget is still exceeded, fail with the role and measured size; do not silently lower dimensions, crop or ship an oversized fallback. Visually verify text-heavy graphics during migration.

Dark artwork gets its own asset descriptor and responsive renditions. Social metadata intentionally uses the light asset. About retains the existing default social image rather than cropping the portrait into a new card.

## Validation and tests

Routine verification checks descriptors, source dimensions, referenced identities, finite role sets, declared byte budgets and emitted URLs locally. `npm run validate-images` remains an explicit operator verification command: deduplicate URLs, bound concurrency/bytes and decode each public rendition at most once per run. It does not fetch private originals. Do not add live Blob requests to nightly tests.

Tests must cover observable contracts, in keeping with AGENTS.md:

- Published content cannot use a missing/malformed descriptor or direct original URL; incomplete drafts remain valid.
- Unsafe source paths, mismatched dimensions, oversized/animated inputs and unsupported descriptor versions fail before writes.
- Partial upload failure leaves the prior descriptor intact; a verified rerun resumes without overwrites or duplicate versions.
- Light/dark selection, responsive sizes and lazy/eager behavior remain correct in cards, detail pages, carousel and no-script fallback.
- OG/Twitter/JSON-LD agree on public social URL and actual dimensions; private-original data and secret canaries are absent from artifacts.
- A clean build and routine CI succeed with all media network access blocked and both storage credentials absent. No per-asset binary work is done by the site build.
- Public staging data cannot leak into static output.

Run focused unit tests first, then `npm run verify`, `npm run verify:build-purity` and the affected browser qualification. Use representative desktop/mobile layouts, light/dark themes and relevant supported browser checks. Explicit remote readback happens once during publishing/migration, not on every test retry.

## Migration and cutover

1. Inventory the existing store and every repository/runtime reference. Reuse the investigation inventory initially, but refresh metadata before external writes. The known store has 14 objects; 11 source images are actively referenced. Do not treat the other three as authorized deletions.
2. Produce an operator-reviewed migration manifest mapping each old URL to its private source identity and replacement asset key. Download each original only once, into ignored staging, with bounded transfer and a persisted SHA-256. Use local original bytes if already available and verified; the About source is approximately 9.7 MB, so the old validator's 5 MiB limit must not truncate migration.
3. Archive all inventoried originals privately. Generate public rendition sets for currently referenced assets. Record unused objects as archived-only. Any undecodable source or dimension mismatch stops that asset without changing its active reference.
4. Update content and all consumers on the branch; finish descriptor, artifact and browser verification. Set `package.json` and the lockfile application version to 2.4.0. Update the canonical image workflow and release verification record together.
5. Prepare the branch/PR and a concrete deployment cutover checklist for review. A preview must prove the new assets, metadata and rendering before a production promotion. Do not label local tests as deployed verification.
6. After approved production cutover, verify live pages and metadata, then inspect the old PNG's continuing transfer independently. Replacement HTML does not revoke cached social metadata or direct links.
7. Prepare a separate retirement manifest for old public originals. Every target needs a verified private copy, replacement reference coverage, an audit of retained deployments and an explicit rollback disposition. Do not delete while a live deployment still depends on it. Cached older pages/deployments may require rebuilding, protecting or retiring before deletion is safe; present those exact consequences for approval.

The upload command never deletes. Removing already public originals is irreversible from a caller's perspective, even if the bytes are archived privately; obtain approval for the exact retirement targets before execution. No application-domain redirect can intercept requests made directly to the Blob hostname.

## Rollback and completion evidence

Before legacy retirement, rollback uses previous content/descriptor commits and leaves all immutable assets intact. After retirement, rollback must target a release using renditions; reverting to an old original-based release would restore broken references. Preserve the private archive and safe operation receipts.

Implementation is complete when the code and migrated descriptors pass the required checks, builds make zero media reads, the published replacement assets have verified formats/dimensions/budgets, and the reviewable branch contains matching documentation. Production mitigation and old-URL retirement are reported as separate verified states; neither is claimed merely because the code is ready.

## Alternatives considered

- Repository-owned binaries: rejected by the user because the library would grow with Git history and build work.
- Social-tag-only fix: leaves other original exposure and repeat build downloads, and does not stop existing direct original requests.
- Private-original proxy or request-time transformation: adds runtime dependency and transfer paths to a static site; not necessary for a finite publish-time rendition contract.
- Provider migration or paid-plan change: not required for this implementation. Public delivery still consumes bandwidth and must be monitored under the actual quota.
