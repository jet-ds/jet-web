# Schema Visualizer - Feature Specification

## Overview

`Schema Visualizer` is the first concrete tool in the new `Tools` section of jetsanchez.com.

It is a code-authored feature, not CMS-managed content.

The tool allows a user to paste JSON-LD and inspect it through two complementary views:

- `Items`
- `Visualization`

This is intentionally a constrained `v1` of the tool. It is not trying to reproduce the full surface of Classy Schema or other structured data testing tools.

## Product Thesis

Most schema tools are optimized for validation output, raw JSON inspection, or search-engine compliance checks. This tool should instead optimize first for understanding structure.

The product goal is to help a user answer:

- what entities exist in this JSON-LD?
- how are they related?
- what is the main entity?
- what important properties are attached to each item?

The tool should feel polished, calm, and legible rather than developer-rough or demo-like.

## MVP Scope

### Included

1. Paste-only input
2. JSON-LD only
3. Parse-on-submit or parse-on-explicit-action
4. `Items` tab
5. `Visualization` tab
6. Error state for invalid JSON or invalid JSON-LD shape
7. Smooth, polished 2D relationship graph

### Excluded

1. URL fetch
2. Microdata
3. RDFa
4. Rich results / Google compliance validation
5. Exporting images or graph files
6. Multiple visualization modes
7. Schema.org vocabulary docs lookup

## Route Placement

The tool lives under the `Tools` section:

- `/tools`
- `/tools/schema-visualizer`

The `/tools` hub links to this tool as the first fully available tool.

## Target Users

- SEOs
- technical marketers
- developers implementing structured data
- site owners trying to understand JSON-LD already generated by a CMS or plugin

## UX Goals

### Primary UX Goal

Turn pasted JSON-LD into a representation that feels easier to reason about than raw source.

### Secondary UX Goals

- make invalid input handling non-threatening
- make the graph feel premium, not chaotic
- make both tabs derive from the same parsed model so the interface feels coherent

## Core Experience

### Input Panel

The page should provide:

- a large paste area for JSON-LD
- a primary action such as `Visualize`
- optional helper text explaining accepted input
- an example JSON-LD snippet or `Load Example` action if useful

The MVP should not depend on live parsing while typing. Explicit parsing on action is acceptable and likely cleaner.

### Activation Boundary

Heavy runtime work should be deferred until the user explicitly activates the tool.

For `v1`, this means:

- the page shell and paste UI render immediately
- `jsonld` processing and graph runtime are loaded only after the user clicks `Visualize`
- the visualization runtime is rendered client-side only after activation

This keeps the route lightweight before the user commits to processing input.

### Items Tab

The `Items` tab should present extracted entities in a readable structured way.

Each item should clearly surface:

- label or display name
- `@type`
- `@id` if present
- core properties
- obvious nested references

This should not just dump raw JSON. It should be an interpreted view of the normalized entity model.

### Visualization Tab

The `Visualization` tab should render a 2D relationship graph.

The graph should prioritize:

- stable layout
- clarity of relationships
- node readability
- smooth interaction

This is not a novelty graph. It is the visual equivalent of the `Items` tab.

### Shared Selection

The `Items` and `Visualization` tabs must share selection state from day one.

That means:

- selecting an item should focus or highlight its corresponding graph node
- selecting a node should surface the same entity detail model used by the `Items` tab

This is part of the MVP architecture, not a later enhancement.

## Technical Approach

### Semantic Processing

Use `jsonld` as the semantic processing layer for the MVP.

Reasoning:

- standards-based JSON-LD handling
- stronger foundation than ad hoc recursive parsing
- better long-term alignment with real-world JSON-LD edge cases
- reduces the risk of building the visualizer on a misleading or incomplete interpretation of structured data

The tool should still maintain its own internal normalized representation for product use. `jsonld` is the semantic engine, not the final application model.

### Rendering Technology

Use `react-force-graph-2d` for the MVP visualization layer.

Reasoning:

- fast path to a usable graph
- sufficient control over interaction and aesthetics
- better fit than 3D for readability and public polish
- avoids the overhead of building a custom renderer before the data model is proven

### Framework Integration

- Astro page shell
- React island for the interactive tool
- `jsonld` for JSON-LD processing
- local utility modules for normalization and graph transformation

## Internal Data Model

Both tabs must be powered by the same normalized representation.

Recommended pipeline:

1. parse raw JSON
2. validate that input is JSON-LD-like
3. process input through `jsonld`
4. normalize processed output into entities
5. resolve references and nested nodes for application use
6. produce:
   - `items[]`
   - `nodes[]`
   - `links[]`

The graph should be a view over the normalized items model, not a second parsing path.

### Suggested Entity Shape

```ts
type VisualizerEntity = {
  id: string;
  type: string[];
  label: string;
  rawId?: string;
  properties: Record<string, unknown>;
  relationships: Array<{
    predicate: string;
    targetId: string;
  }>;
};
```

### Suggested Graph Shape

```ts
type GraphNode = {
  id: string;
  label: string;
  types: string[];
  kind: 'root' | 'entity' | 'value';
  degree: number;
};

type GraphLink = {
  source: string;
  target: string;
  label: string;
};
```

## Parsing Rules

### Accepted Input

The MVP accepts:

- a JSON object
- a JSON array
- a JSON-LD object containing `@context`, `@type`, `@graph`, or nested schema entities

### Supported Structures

The MVP should support:

- single entity object
- multiple top-level entities
- `@graph`
- nested objects that are meaningful entities
- `@id` references where present

### Processing Expectation

The tool should use `jsonld` to handle JSON-LD semantics before the UI-level normalization step.

This does not remove the need for application-specific logic. The tool still needs its own rules for:

- choosing item labels
- identifying likely primary entities
- deciding which properties become graph edges
- deciding which properties remain scalar display fields

### Context Support Policy

`v1` officially supports schema.org JSON-LD contexts only.

This means:

- `https://schema.org` and `https://schema.org/` should be bundled or resolved locally through a custom `documentLoader`
- arbitrary remote contexts should not be fetched freely in the browser
- unsupported remote contexts should fail gracefully with a clear user-facing message

This is an intentional scope boundary for the MVP.

### Graceful Limitations

If input is valid JSON but not meaningfully interpretable as JSON-LD, show a clear message rather than pretending to understand it.

## Visualization Requirements

### Aesthetic Requirements

The graph must feel:

- smooth
- deliberate
- readable
- premium

It must not feel:

- chaotic
- physics-toy-like
- default-library-styled
- visually noisy

### Interaction Requirements

The visualization should support:

- pan
- zoom
- hover feedback
- selection
- synchronized detail display for selected nodes

### Mobile Interaction

The graph is included on mobile in `v1`.

This is a deliberate requirement, not a desktop-only experience. The implementation must account for the tension between:

- page scrolling
- graph panning
- node dragging
- zoom gestures

The mobile interaction model should be designed intentionally rather than treated as polish. If necessary, node dragging can be reduced or constrained on touch devices to protect usability.

For `v1`, touch devices should prefer scroll-safe behavior over full drag freedom. If needed, node dragging should be reduced or disabled by default on touch screens while preserving tap selection, pan, and zoom.

### Layout Requirements

The graph should prefer:

- restrained force simulation
- quick settling
- low jitter after initial render
- stable positions during interaction where practical

### Node Rendering

Nodes should use custom drawing rather than default circles alone.

Minimum visual treatment:

- differentiated color treatment by node kind or type
- readable label treatment
- selected-node emphasis
- root/main entity emphasis

### Edge Rendering

Edges should:

- be visually subdued by default
- become clearer on selection/hover
- support readable relationship labels where practical

## Items Tab Requirements

Each item card or row should support:

- clear title
- type badge(s)
- `@id` display when present
- list of key properties
- ability to focus and select the corresponding node in the graph

The items view should feel like a clean inspector, not a raw debug dump.

## Error Handling

The tool must distinguish between:

1. invalid JSON
2. valid JSON but not interpretable as useful JSON-LD
3. valid JSON-LD with odd structure but still renderable

Error messaging should be concise and calm.

## Performance Expectations

The MVP is optimized for small to medium pasted snippets, not huge enterprise schema graphs.

The visualization should remain smooth for typical schema inputs such as:

- Article
- FAQPage
- Product
- Organization
- LocalBusiness
- BreadcrumbList
- WebSite / SearchAction

If an input is too large or too dense, the tool should degrade gracefully rather than attempting to render an unreadable graph.

## Accessibility Requirements

- keyboard-accessible tabs
- readable contrast
- focus states
- graph interactions should not be the only path to understanding the data
- the `Items` tab must remain fully usable as a non-graph fallback

## SEO and Product Positioning

This tool is a public page and should be indexable.

The page should be positioned as:

- a schema markup visualization tool
- a structured data understanding tool

It should not claim to be a full compliance validator in the MVP.

## Example Content

The MVP should include one strong built-in schema.org example payload.

This example should:

- be realistic
- exercise multiple entities and relationships
- be complex enough to make both tabs meaningful
- be easy to load into the input area

Chosen example:

- Article + WebPage + Person + Organization graph

The example is part of the onboarding experience, not filler.

## Design Direction

The page should fit the site's visual language while still feeling tool-like.

Suggested page composition:

1. Intro / title
2. Short explanation of what the tool helps with
3. Input panel
4. Results area with tabs
5. Optional small note about MVP limitations

The results area should feel substantial and focused, with the graph treated as the visual centerpiece when the `Visualization` tab is active.

## Future Extensions

### Likely Next Steps

- URL fetch
- Microdata parsing
- schema.org term links
- warnings / validation layer
- richer examples
- graph export / screenshot export
- side-by-side raw JSON view

### Explicitly Deferred

- Google Rich Results validation
- backend ingestion pipeline
- AI-assisted schema generation
- collaborative sharing

## Implementation Plan

### Phase 1: Data Model and Parsing

1. Define TypeScript types
2. Implement JSON parsing
3. Integrate `jsonld` and inspect output shapes for representative examples
4. Normalize processed JSON-LD into entities and relationships
5. Add representative example fixtures

### Phase 2: Page and Tabs

1. Create `/tools/schema-visualizer`
2. Build input panel
3. Build tab shell
4. Add built-in example-loading flow
5. Render parsed entities in `Items`
6. Update `/tools/index.astro` to surface Schema Visualizer as the first live tool

### Phase 3: Visualization

1. Add `react-force-graph-2d`
2. Transform normalized entities into graph nodes/links
3. Implement shared selection state between `Items` and `Visualization`
4. Implement custom node and edge drawing
5. Tune force settings for stable motion
6. Design and validate mobile graph interaction behavior

### Phase 4: Polish

1. Improve labels and selection states
2. Improve empty/error states
3. Validate mobile and desktop behavior

## Success Criteria

The MVP is successful if:

1. A user can paste common JSON-LD and get a useful result
2. The `Items` tab makes the data easier to inspect than raw JSON
3. The `Visualization` tab feels smooth and polished rather than gimmicky
4. The tool looks like a real product feature, not a developer sandbox
5. The tool is discoverable from `/tools`
